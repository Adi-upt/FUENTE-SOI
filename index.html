SECCIÓN 01

1. Resumen Ejecutivo

Se propone diseñar una aplicación web para consultar documentación técnica mediante lenguaje natural, utilizando Generación Aumentada por Recuperación (RAG) para localizar información de manuales en una memoria no paramétrica externa (Lewis et al., 2020) y el estándar abierto Model Context Protocol (MCP) para consultar herramientas externas de forma controlada mediante JSON-RPC 2.0 (Anthropic, 2024; Model Context Protocol, 2025). El propósito es facilitar el acceso a procedimientos y conocimientos de soporte técnico cuando un especialista no se encuentra disponible de inmediato.

La aplicación web se publicará en Microsoft Azure (MATTEO-01) empleando Java / Spring Boot bajo una arquitectura hexagonal (Domain, Application/Service e Infrastructure). El motor ProjectSevera, ejecutado mediante Python, FastAPI y PyTorch en el nodo local MATTEOXPC, se encargará de la ingesta documental, la generación de embeddings, la búsqueda en el índice vectorial y la síntesis de respuestas fundamentadas. La administración de archivos PDF estará restringida a una única cuenta protegida con Spring Security y BCrypt, mientras que las consultas de usuarios comunes serán públicas sin exigir registro.

Delimitación epistemológica: La primera versión constituye un prototipo académico de alcance controlado. Sus umbrales de precisión, comportamiento temporal, tolerancia a fallos y seguridad representan metas de diseño que se medirán empíricamente en la Unidad III.
SECCIÓN 02

2. Planteamiento del Problema

2.1. Situación Actual

En entornos de soporte técnico, las instrucciones para configurar y operar aplicaciones, dispositivos y servicios se encuentran distribuidas entre manuales extensos, guías de resolución de problemas (troubleshooting guides) y procedimientos internos (Ahmed et al., 2023; Toro Isaza et al., 2025).

La dificultad no radica únicamente en la existencia de los documentos: intervienen la brecha léxica entre el lenguaje coloquial del usuario y la terminología técnica de los manuales (Robertson y Zaragoza, 2009; Karpukhin et al., 2020), la fragmentación de contexto en repositorios planos (Xu et al., 2024; González Juclà et al., 2024) y la necesidad de relacionar múltiples pasajes durante varios turnos conversacionales (Feng et al., 2020, 2021; Chen et al., 2024b).

2.2. Necesidad Identificada

Se requiere un medio accesible que permita consultar documentación técnica en lenguaje natural, recuperar fragmentos pertinentes y ofrecer explicaciones vinculadas a fuentes identificables (Gao et al., 2023b; Friel et al., 2024).

Los modelos de lenguaje aislados tienden a producir alucinaciones fácticas cuando responden sobre procedimientos específicos fuera de su conocimiento paramétrico (Ji et al., 2023; Shuster et al., 2021; Adlakha et al., 2024). Asimismo, la ingeniería de sistemas RAG debe mitigar puntos de fallo conocidos en el particionamiento de tablas y filtrado de ruido documental (Barnett et al., 2024; Roy et al., 2024; Barrionuevo-Valenzuela et al., 2025).

2.3. Justificación de la Propuesta

La integración de RAG y MCP separa dos responsabilidades distintas: recuperar conocimiento textual desde manuales actualizables (Lewis et al., 2020; Guu et al., 2020; Gao et al., 2024) y consultar información operativa mediante herramientas de solo lectura bajo un protocolo estandarizado que evita el cableado manual de APIs (Yao et al., 2025; Anthropic, 2024; Model Context Protocol, 2025; Hou et al., 2026).

Dado el riesgo de inyección indirecta de prompts en documentos externos (Greshake et al., 2023; Zhan et al., 2024), el diseño impide que una instrucción dentro de un PDF adquiera privilegios de ejecución.

SECCIÓN 03

3. Objetivos

3.1. Objetivo General

Diseñar una aplicación web de asistencia técnica basada en RAG y MCP que permita consultar documentación mediante lenguaje natural y obtener información fundamentada en fuentes verificables (Gao et al., 2023b), utilizando una infraestructura distribuida entre Azure y un equipo local de procesamiento de inteligencia artificial.

3.2. Objetivos Específicos

OE-01

Diseñar un módulo de gestión documental que permita incorporar, almacenar, listar y retirar manuales técnicos en formato PDF manteniendo sincronía con el índice vectorial.

OE-02

Diseñar un sistema de consultas RAG que recupere evidencia relevante y genere respuestas vinculadas a documentos, incluyendo abstención explícita cuando la información resulte insuficiente (Asai et al., 2024; Yan et al., 2024).

OE-03

Establecer la integración con herramientas MCP autorizadas para obtener información operativa de solo lectura bajo validación estricta (Hou et al., 2026).

OE-04

Definir la arquitectura hexagonal, la infraestructura híbrida, los controles de seguridad y el plan de pruebas necesarios para implementar y validar el prototipo en la Unidad III.

SECCIÓN 05

5. Diseño de la Arquitectura

5.1. Arquitectura Lógica Hexagonal

El backend en Java con Spring Boot aplica el patrón de Puertos y Adaptadores (Cockburn, 2005), dividido en tres capas: Domain (entidades Document y ConversationContext), Application / Service (casos de uso AskQuestionUseCase, ManageDocumentUseCase, QueryMcpToolUseCase y puertos AiProcessingPort, DocumentRepositoryPort, McpToolPort) e Infrastructure (controladores REST y adaptadores de salida PythonAiAdapter, McpClientAdapter, FileDocumentRepositoryAdapter). Así, la lógica de dominio no depende directamente de PyTorch ni del transporte MCP (Schick et al., 2023; Yao et al., 2023; Hou et al., 2026).

5.2. Arquitectura Física y Despliegue

El despliegue físico comprende dos nodos interconectados por una VPN privada Tailscale (Modran, 2025; Gao et al., 2024): la máquina virtual Azure MATTEO-01 aloja IIS, el backend Spring Boot, el servidor MCP de solo lectura y el repositorio de archivos PDF junto con metadata.json; mientras que la estación de trabajo MATTEOXPC ejecuta la API privada en FastAPI, el motor ProjectSevera sobre PyTorch y el índice vectorial local (Johnson et al., 2019; Malkov y Yashunin, 2020).

5.4. Flujo de Información de los Cuatro Casos de Uso

En CU-01, el usuario envía su pregunta a Spring Boot, que la transmite por Tailscale hacia FastAPI/ProjectSevera para recuperar evidencia del índice vectorial y devolver una respuesta citada o abstención (Asai et al., 2024; Yan et al., 2024). En CU-03, si la consulta requiere verificar un estado operativo, el servicio de aplicación valida la herramienta en su lista permitida e invoca al servidor MCP en modo de solo lectura (Modran, 2025; Ghafourian et al., 2025). En CU-04 y CU-02, el administrador se autentica con Spring Security y carga o retira archivos PDF, sincronizando su estado en metadata.json y en el índice vectorial local.

SECCIÓN 06

6. Diseño de Infraestructura

6.1. Servidores y Equipos

  • Servidor Nube (Azure MATTEO-01): Instancia IaaS tamaño Standard B2as v2 con 2 vCPU y 8 GiB de RAM (Microsoft Corporation, 2024). Aloja la publicación web HTTPS, el backend Java Spring Boot, Spring Security, el servidor MCP y los archivos PDF/JSON.
  • Equipo Local de IA (MATTEOXPC): Estación de trabajo equipada con procesador Intel Core i7-14700F, 64 GB de RAM y GPU NVIDIA GeForce RTX 5070 Ti (16 GB VRAM). Dedicada a ejecutar FastAPI, PyTorch, ProjectSevera y la búsqueda de similitud en el índice vectorial (Johnson et al., 2019; Gao et al., 2024).

6.2. Sistemas Operativos y Virtualización

  • Sistemas Operativos: Windows Server 2022 Datacenter en la máquina virtual Azure MATTEO-01 y sistema operativo Windows en la estación local MATTEOXPC.
  • Esquema de Virtualización: Se emplea virtualización de infraestructura como servicio (IaaS) provista por Microsoft Azure para el nodo web, mientras que MATTEOXPC opera directamente sobre hardware físico para acceder sin sobrecarga a los 16 GB de VRAM de la GPU RTX 5070 Ti mediante CUDA/PyTorch, prescindiendo de hipervisores intermedios como Proxmox.

6.3. Almacenamiento y Sincronización

En esta primera versión se prescinde de motores relacionales como PostgreSQL. Los manuales originales en PDF y el archivo de control metadata.json se almacenan en un directorio protegido de MATTEO-01.

El archivo metadata.json registra el identificador único de cada documento y su estado (pendiente, procesado, error o eliminado), asegurando que cualquier PDF retirado en Azure sea purgado del índice vectorial en MATTEOXPC (González Juclà et al., 2024; Xu et al., 2024).

6.4. Servicios Requeridos y Restricciones

  • • IIS + Certificado HTTPS (Azure): Publicación web en puerto TCP 443.
  • • Spring Boot + Spring Security (Azure): Escucha interna en 127.0.0.1:8080.
  • • Servidor MCP solo lectura (Azure): Consumo local desde el backend Java.
  • • Tailscale VPN (Azure y PC): Interconexión cifrada autenticada (Donenfeld, 2017).
  • • FastAPI + ProjectSevera (PC Local): API privada en puerto TCP 8000.
SECCIÓN 07

7. Diseño de Red

7.1. Topología, Segmentación y 7.3. Equivalencia VLAN

La topología enlaza a los clientes web con MATTEO-01 mediante HTTPS (TCP 443) y conecta a la máquina virtual de Azure con MATTEOXPC a través de una red privada virtual punto a punto con Tailscale (Donenfeld, 2017). Se establecen tres zonas de segmentación lógica: (1) Zona pública de acceso HTTPS, (2) Zona interna de aplicación y MCP en loopback (127.0.0.1) y (3) Zona privada de inferencia IA sobre la interfaz Tailscale.

Justificación sobre VLAN: El prototipo no implementa etiquetas IEEE 802.1Q físicas porque no opera sobre conmutadores L2 corporativos locales; el aislamiento de red se ejecuta mediante Azure Virtual Network (vnet-chilecentral-1 / snet-chilecentral-1) y el plano cifrado de Tailscale (Microsoft Corporation, 2024).

8.2. Controles y Estrategias de Mitigación (E-01 a E-05)

Los controles propuestos se articulan con las familias técnicas de NIST SP 800-53 Rev. 5 (NIST, 2020):

E-01 (Mitiga R-01 | NIST AC-2, IA-2): Login ADMIN mediante Spring Security con usuario único en memoria y hash BCrypt (VMware, 2024); autorización obligatoria para carga y eliminación de PDF.
E-02 (Mitiga R-02, R-04 | NIST SI-10): Validación de extensión, tipo MIME y tamaño de PDF; delimitación estricta entre pasajes recuperados (datos no confiables) e instrucciones de sistema; abstención ante falta de evidencia.
E-03 (Mitiga R-02, R-03 | NIST AC-6): Lista blanca corta (allowed_tools) en Java y en el servidor MCP restringida exclusivamente a operaciones de solo lectura con validación de parámetros (Modran, 2025; Hou et al., 2026).
E-04 (Mitiga R-05 | NIST SC-7, SC-8): Exposición única por HTTPS (443), ocultamiento de puertos internos (8080/8000), reglas NSG, Windows Firewall y túnel cifrado Tailscale.
E-05 (Mitiga R-06, R-07 | NIST CP-9, AU-2, SI-4): Respaldos diarios externos con prueba de restauración, monitoreo de disponibilidad y mensajes de fallo controlados en ≤ 10 s.

8.4. Gestión de Accesos

  • Usuario público: Consultar IA y solicitar lecturas MCP previamente permitidas.
  • Administrador: Consultar IA, iniciar sesión, cargar, listar y eliminar PDF.
  • Servicio Java: Consumir API Python por VPN e invocar herramientas MCP locales permitidas.
  • Servicio Python: Indexar y responder consultas; sin privilegios sobre credenciales ni sobre Azure.

8.5. Respaldo y Recuperación

Se programan respaldos diarios automatizados de los archivos PDF originales y de metadata.json hacia almacenamiento externo independiente, conservando una retención inicial de 7 copias y ejecutando al menos una prueba de restauración verificada (PN-05).

No se promete un RTO empresarial continuo dado que MATTEOXPC es un nodo único sin clúster de alta disponibilidad.

8.6. Monitoreo y Auditoría

Se emplearán las métricas básicas del portal de Azure, el Visor de eventos de Windows Server 2022 y los archivos de registro (logs) de Spring Boot, FastAPI y el servidor MCP. Cada evento registrará marca temporal, identificador de operación, estado y actor, prohibiendo almacenar contraseñas en texto plano o hashes de sesión en los logs (NIST, 2020; Hou et al., 2026).

SECCIÓN 09

9. Diseño Operativo

9.1. Roles y Responsabilidades

  • • Administrador documental: Autenticarse como ADMIN; cargar, listar y retirar PDF; verificar estado de indexación.
  • • Responsable de backend: Mantener Spring Boot, puertos/adaptadores, seguridad y logs.
  • • Responsable de IA: Operar ProjectSevera, FastAPI, embeddings e índice vectorial en MATTEOXPC.
  • • Responsable de infraestructura: Administrar Azure MATTEO-01, Tailscale, firewall y copias de respaldo.

9.2. Procedimiento de Operación

  1. Comprobar encendido y enlace Tailscale entre MATTEO-01 y MATTEOXPC.
  2. Verificar disponibilidad de IIS, Spring Boot, servidor MCP y FastAPI.
  3. Habilitar acceso web HTTPS y ejecutar una consulta documental de control.
  4. Ejecutar altas o bajas de PDF exclusivamente tras iniciar sesión ADMIN.
  5. Auditar registros ante fallos y verificar aviso de indisponibilidad si se apaga la PC.

9.3. Mantenimiento Preventivo

Revisión semanal de espacio en disco en Azure y PC local, consistencia entre los archivos PDF físicos, el registro metadata.json y los vectores en ProjectSevera (Barnett et al., 2024), estado de sesiones VPN en Tailscale y validez de las copias de respaldo externas (Hasan et al., 2025).

SECCIÓN 12

12. Análisis de Factibilidad

12.1. Factibilidad Técnica

El prototipo es técnicamente viable porque se dispone tanto de la máquina virtual MATTEO-01 en Azure como de la estación local MATTEOXPC (i7-14700F, 64 GB RAM, RTX 5070 Ti 16 GB VRAM). Esta separación delega el cómputo tensorial de PyTorch y ProjectSevera al equipo con GPU dedicada, evitando saturar los 8 GiB de RAM de la instancia Azure (Johnson et al., 2019; Modran, 2025; Toro Isaza et al., 2025).

12.2. Factibilidad Económica (Supuestos en Soles)

Dado que MATTEOXPC es un equipo preexistente (CAPEX de hardware S/ 0,00 para el prototipo), la estimación considera hipótesis presupuestarias referenciales (tipo de cambio S/ 3,423/USD y tarifa eléctrica supuesta S/ 0,80/kWh):

  • • Azure VM (~US$ 100/mes): S/ 342,29 / mes
  • • Electricidad media (0,9 kW × 720 h): S/ 518,40 / mes
  • • Mantenimiento equiv. (8 h × S/ 15,63): S/ 125,00 / mes
  • • Costo mensual medio estimado: S/ 985,69 / mes
  • *(Rango entre S/ 812,89 y S/ 1.158,49 según carga de 0,6 a 1,2 kW; desarrollo inicial equivalente: S/ 937,50 por 60 h)*.

12.3. Factibilidad Operativa

La operación resulta manejable para el equipo universitario asignando responsables de arranque, gestión de PDF y respaldo. Los usuarios finales solo requieren un navegador web sin registro previo (RF-01). La principal restricción operativa es la dependencia del encendido y conexión de MATTEOXPC, mitigada mediante horarios de demostración y avisos controlados de indisponibilidad (Roy et al., 2024; Barrionuevo-Valenzuela et al., 2025).

SECCIÓN 13

13. Conclusiones

1. Separación arquitectónica entre RAG y MCP: El diseño consolida una solución de soporte técnico documental que desacopla la recuperación textual sobre manuales PDF respecto de la consulta operativa en herramientas externas de solo lectura, evitando exponer funciones de administración al modelo generativo.
2. Desacoplamiento mediante Arquitectura Hexagonal: La estructura en capas Domain, Application/Service e Infrastructure en Spring Boot permite aislar las reglas de negocio de los adaptadores hacia FastAPI/ProjectSevera, el almacenamiento local y el servidor MCP.
3. Aprovechamiento híbrido de recursos reales: La combinación de la máquina virtual MATTEO-01 en Azure con la GPU RTX 5070 Ti en MATTEOXPC a través de Tailscale viabiliza la ejecución local de modelos de lenguaje sin incurrir en costos de instancias GPU en la nube, reconociendo explícitamente la dependencia de disponibilidad del nodo local.
4. Compromisos verificables hacia la Unidad III: Los controles de seguridad (E-01 a E-05), los umbrales de calidad (RNF-01 a RNF-11) y el presupuesto en soles se establecen como metas e hipótesis transparentes cuya comprobación empírica se ejecutará mediante las pruebas PF-01–PF-08 y PN-01–PN-11.
